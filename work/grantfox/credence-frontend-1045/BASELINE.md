## What is already implemented

This bounty should not duplicate work that is already on main.

### OpenAPI code generation already exists

`package.json` already declares:

```
"generate:api": "openapi-typescript openapi.yaml -o src/api/generated.ts"
```

and declares `openapi-typescript` as a dev dependency with range `^6.7.6`. The lockfile is checked in, so CI should use `npm ci` and the lock rather than resolving the semver range afresh.

`src/api/generated.ts` is checked in and identifies itself as generated by `openapi-typescript`.

Historical merged PR #478 introduced this pipeline and the generated/public API type layer. This is important provenance: #1045 is not asking for first-time code generation anymore; it is asking for reproducibility enforcement and completion of operation-level usage.

### Public generated aliases already exist

`src/api/types.ts` imports `components` from `generated.ts`, re-exports generated `components`, `operations`, and `paths`, and derives:
- `BondStatus`
- `TrustTier`
- `TrustScore`
- `Bond`
- `Transaction`
- `ApiMessageResponse`
- `Tenant`

It also defines `ApiResponse<Op>` for a 200 JSON response body.

These aliases are useful compatibility surfaces, but a schema alias does not couple a call site to the exact path/operation that returned it.

### Transactions already use operation-level response typing

`src/hooks/useTransactions.ts` defines:

```ts
type TransactionsResponse = ApiResponse<operations['listTransactions']>
```

and passes that type to `apiFetch`.

Merged PR #1021 made this migration. Repeating it would be duplicate work.

### Trust score does not yet use the operation type

`src/hooks/useTrustScore.ts` imports the schema alias `TrustScore` and calls:

```ts
apiFetch<TrustScore>(`/trust-score/${...}`)
```

The checked-in docs already show the stronger intended form:

```ts
ApiResponse<operations['getTrustScore']>
```

The source therefore contains a concrete residual drift seam: the contract has an operation type, but the production trust-score hook is not using it.

## Canonical OpenAPI coverage gap: Bond has a schema but no operation

At the pinned head, `openapi.yaml` exposes these paths:
- `GET /trust-score/{address}` → `getTrustScore`
- `GET /transactions` → `listTransactions`
- `PATCH /settings` → `updateSettings`

It defines a reusable `Bond` schema but **no bond path or bond operation**.

The architecture documentation also states that `Bond.tsx` uses a hardcoded `initialBonds` collection and in-memory transitions.

This creates a hard dependency for the issue acceptance language around "representative contract fixtures for bond": a contributor must not invent a `POST /bonds`, `GET /bonds`, or other endpoint just to satisfy the issue. The authoritative backend contract must first be added to `openapi.yaml` (or the maintainers must explicitly scope "bond fixture" to schema-only validation).

That dependency should be surfaced before implementation, not hidden behind a broad `Bond` cast.

## CI is currently incapable of detecting generated drift

The entire checked-in workflow at `.github/workflows/ci.yml` has one quality-gate job whose only active command is an echo explaining that the quality gate is paused while CI stabilization is in progress.

Consequences:
- no `npm ci`;
- no `npm run generate:api`;
- no diff check on `src/api/generated.ts`;
- no TypeScript build/type check;
- no contract tests;
- no lint/test gate.

The safest #1045 implementation is therefore a **separate focused API-contract job**. It should not pretend the paused broad quality gate is healthy or require reopening unrelated failures just to protect OpenAPI drift.

## Compile-time typing is not runtime validation

The current `apiFetch<T>` transport parses successful JSON and returns it as `T`. Its generic parameter does not validate server bytes at runtime.

That means a 200 response such as:
- a trust score missing `tier`;
- a trust score with an unknown tier string;
- `score: "840"` instead of a number;
- a transaction list whose `items` is not an array

can pass the transport boundary and fail later in UI logic even if TypeScript is perfectly clean.

Issue #1045 explicitly asks for malformed/unexpected response handling, so generated compile-time types alone cannot close the bounty.
